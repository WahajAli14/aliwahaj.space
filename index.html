The problem

Selected high-volume endpoints took 20 seconds to respond. Repeated related-data queries added avoidable work to the backend.

My contribution

I improved SQLAlchemy queries and removed N+1 issues. I also implemented Redis caching for frequently accessed data and moved heavy reports and image-change workflows to AWS SQS.

Engineering rationale

Removing N+1 queries reduces repeated related-data reads at their source. Caching can reduce repeated work further; queueing heavy jobs keeps that work outside the request path. These mechanisms solve different bottlenecks.

A decision worth showing

Reusable distance records reduced 100K+ monthly Mapbox calls to near zero. The records expired after three months to keep location data updated.

Evidence and scope

The 70% reduction applies to the selected endpoints described in my résumé. Redis improved selected workflows by approximately 50%; that is a separate result. Insight MCP

Giving an AI client access to data means deciding what it may read, what it must reject, and how much work a request can do.

Read reasoning & evidenceClose reasoning+

The problem

A model’s instructions are not a database permission boundary. A useful data tool needs checks that still apply when a client submits an unexpected query.

What I built

A Python MCP project with SQL discovery and read-only query tools, plus a separate dataset-profiling server. The SQL path combines parsed-query validation with a least-privilege PostgreSQL role and read-only transactions.

Why two layers

The query policy inspects the SQL structure, including nested statements, before execution. Database permissions provide another boundary. Neither layer should depend on a model following a prompt.

Bound the response and the work

The implementation returns at most 100 rows and applies a 5-second statement deadline. The row cap limits the response size; the deadline limits how long the database statement may run. They address different costs.

What I verified

The existing SQL-policy suite passed 22 tests locally on 5 November 2026, covering accepted reads, writes, stacked statements, nested writable queries and disallowed table references.

Evidence and limits

The implementation and tests were reviewed from the private repository. The 22 passing checks cover query validation. PostgreSQL integration, timeout enforcement and the database permission boundary were not executed in this portfolio review. This is not a production deployment, a customer outcome or a complete security assessment. Source code remains private.

Fuel Route Optimizer

Where should a truck refuel, how much should it buy, and what will the trip cost?

The constraint

Plan fuel stops for a truck with a 500-mile range at 10 miles per gallon, using available station prices along a U.S. route.

The implementation

The Django API combines routing, local place lookup, station matching and fuel-stop optimization. An uncached request makes one routing-provider call; a cache hit makes none.

Why this structure

Keeping place lookup and station matching local avoids adding provider calls for every candidate stop. Caching reuses a completed route result; it does not replace the optimization algorithm.

What the evidence shows

The repository’s Dallas-to-Houston example covers 238.7 miles and reports $65.84 in fuel. The published response-time comparison uses the in-memory cache. Redis is optional.

Limits of the result

The routing result depends on the project’s fuel-price dataset and assumptions. It is not a quote for current pump prices. Station locations use city coordinates, and detours are approximated; inspect the README before interpreting the result.
